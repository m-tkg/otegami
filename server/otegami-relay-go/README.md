# otegami-relay-go

Go port of `server/otegami-relay` (Swift/Hummingbird) — Task #180.

## Why port this to Go

The Swift relay's container image targets `arm64` (Raspberry Pi). Building
it on GitHub Actions' `x86_64` runners under QEMU takes **~2.5 hours**,
which eats into the Free plan's 2,000 minutes/month for private
repositories. Native `arm64` runners are free only for **public**
repositories, so the build repo has been temporarily made public to cope —
the goal is to go back to private.

Go cross-compiles to `arm64` natively (`GOARCH=arm64 go build`, no QEMU),
builds in minutes, and produces a single static-ish binary. This directory
is that port. The Swift relay (`server/otegami-relay`) stays in the repo
and in production until this port is verified equivalent end to end; see
"Status" below for what that means concretely.

## Compatibility contract

This is a **byte-for-byte wire and storage compatible** reimplementation,
not a redesign:

- Same HTTP API (`POST /v1/devices`, `PUT /v1/devices/:id/token`, `POST
  /v1/watches`, `GET /v1/watches`, `DELETE /v1/watches/:id`, `GET
  /health`), same JSON field names, same status codes, same auth scheme
  (`Authorization: Bearer <deviceSecret>`). The app
  (`packages/OtegamiKit/Sources/PushRelayClient`, `OtegamiRelayAPI`) is
  **not modified** for this port and must not need to be.
- Same SQLite schema (`device`/`watch` tables, same column names/types,
  same `PRAGMA table_info`-guarded migration approach for older
  databases) — an existing production database opens and reads correctly
  under this binary with no explicit migration step.
- Same AES-256-GCM credential encryption (`RELAY_MASTER_KEY`), same
  "combined" byte layout (nonce‖ciphertext‖tag) swift-crypto's
  `AES.GCM.SealedBox.combined` produces. See
  `internal/cryptox/credential_crypto.go`'s doc comment and
  `internal/cryptox/credential_crypto_test.go` for the cross-
  implementation fixtures (real ciphertext generated by the Swift relay's
  exact code path, decrypted here) and
  `internal/store/store_test.go`'s `TestOpensRealSwiftProducedDatabase`,
  which opens an actual SQLite file produced by running the unmodified
  Swift relay's HTTP API end to end.
- Same environment variables, same names/defaults/semantics
  (`RELAY_MASTER_KEY`, `RELAY_PORT`, `RELAY_DATABASE_PATH`, `APNS_*`,
  `RELAY_DEVICE_REGISTRATION_SECRET`, `RELAY_GOOGLE_CLIENT_ID`,
  `RELAY_MICROSOFT_CLIENT_ID`, `RELAY_EXTRA_IMAP_PORTS`,
  `RELAY_ALLOW_PRIVATE_IMAP_HOSTS`) — an operator's existing `.env`/
  `docker-compose.yml` works unchanged.

## Layout

```
cmd/otegami-relay/       # main() — wires everything together
internal/api/            # wire DTOs (mirrors OtegamiRelayAPI.swift)
internal/cryptox/        # AES-256-GCM credential encryption (CredentialCrypto)
internal/store/          # SQLite persistence (RelayStore)
internal/security/       # SSRF network policy + IMAP control-char validation
internal/httpapi/        # HTTP routes (DeviceRoutes/WatchRoutes)
internal/config/         # environment variable parsing (RelayConfiguration)
internal/imapclient/     # minimal hand-rolled IMAP client (MinimalIMAPClient)
internal/oauth/          # OAuth refresh-token exchange (OAuthTokenExchanger)
internal/push/           # APNs sender + console fallback (PushSending)
internal/watcher/        # per-watch IDLE loop pool (WatcherPool)
```

Each package's doc comment names the exact Swift file it mirrors.

## Library choices

- **SQLite: `modernc.org/sqlite`** (pure Go, no cgo). Chosen specifically
  so cross-compiling for `arm64` needs no C cross-toolchain — using a
  cgo-based driver (`mattn/go-sqlite3`) would reintroduce exactly the
  cross-compilation friction this port exists to eliminate.
- **JWT (APNs ES256 token auth): `golang-jwt/jwt/v5`** — well-maintained,
  supports ES256 out of the box; the alternative (hand-rolling JWT header/
  claims/signing the way the Swift relay does, since swift-crypto has no
  JWT helper) was considered but a dedicated JWT library is the more
  idiomatic Go choice here and doesn't carry the cross-compilation
  concerns a C library would.
- **IMAP: hand-rolled** (`internal/imapclient`), not `github.com/emersion/
  go-imap`. Same rationale `MinimalIMAPClient.swift`'s doc comment gives
  for the Swift side: the actual surface needed is `LOGIN`/`AUTHENTICATE
  XOAUTH2`/`SELECT`/`STATUS`/`IDLE`/`LOGOUT` over plain CRLF-terminated
  lines (no IMAP literals ever appear in these commands' responses), and
  the CLAUDE-SECURITY F2/F3/F4/F8 defenses (SSRF re-validation on every
  reconnect, control-character rejection, untagged-line/byte/deadline
  bounds) need to sit directly on the connection's read/write path rather
  than being retrofitted onto a general-purpose IMAP library's abstractions.
- **HTTP routing: standard library `net/http.ServeMux`** (Go 1.22+'s
  method+wildcard routing, e.g. `"DELETE /v1/watches/{id}"`) — no router
  framework needed for six routes; keeps the dependency graph minimal for
  the same cross-compilation-simplicity reason as the SQLite driver choice.
